## 1. Каркас документа плана

- [x] 1.1 Создать `docs/project-plan.md` с заголовком, назначением и навигацией по [DOC-014](../../../rules/documentation-rules.md#структура-файла); проверка — файл содержит все три обязательных элемента, уровни заголовков идут без пропусков
- [x] 1.2 Зафиксировать единый язык проекта: профиль, измерение, модуль, слой, роль, план структуры, узел, пакет измерения, бэкенд рендеринга; проверка — каждое понятие раскрыто один раз в каноническом формате [TERM-004](../../../rules/terminology.md#ввод-аббревиатуры-в-тексте), далее по тексту используется только закреплённая форма

## 2. Содержание плана

- [x] 2.1 Раздел «Технологическое решение»: выбор Go, таблица сравнения кандидатов и три довода (абстракции стандартной библиотеки, единый бинарник без рантайма, самоприменимость); проверка — названы отклонённые альтернативы с причиной отклонения
- [x] 2.2 Раздел «Модель решения»: двухфазное преобразование «профиль → план структуры → дерево на диске» с диаграммой; проверка — диаграмма показывает, что язык подключается только на последнем шаге, и в тексте объяснено, почему это превращает произведение вариантов в сумму
- [x] 2.3 Раздел «Определение готовности»: сборка, линтер, тесты-заготовки, совпадение с эталоном; проверка — перечислены все четыре условия и разграничены golden-тесты (в памяти) и приёмочные тесты (тулчейн целевого языка)
- [x] 2.4 Раздел «Карта change'ей»: этапы 0–10, у каждого имя будущего change, границы и критерий готовности; проверка — критерий готовности указан у каждого change, экзамен второго языка стоит до расширения контента измерений
- [x] 2.5 Раздел «Границы первой версии»: дорастить существующую структуру, генерация бизнес-логики, миграций и пайплайнов, плагины в виде исполняемого кода — вне первой версии; проверка — каждый пункт назван явно как не входящий в объём

## 3. Процедура приёмки

- [x] 3.1 Раздел «Журнал приёмки» с таблицей «итерация, дата, решение, причина отказа, ответная доработка»; проверка — таблица присутствует с заготовкой первой итерации, формат таблицы стандартный Markdown по [DOC-017](../../../rules/documentation-rules.md#таблицы-doc-017)
- [x] 3.2 Описать цикл ревизий: причина отказа фиксируется до начала доработки, число итераций не ограничено, каждая итерация адресует конкретную зафиксированную причину; проверка — порядок совпадает с решением 8 в [`design.md`](./design.md#decisions)
- [x] 3.3 Завершить документ таблицей версий по [DOC-022](../../../rules/documentation-rules.md#жизненный-цикл-документа); проверка — колонки «Задача», «Агент», «Модель» заполнены, актуальная версия — последняя строка по [DOC-024](../../../rules/documentation-rules.md#жизненный-цикл-документа)

## 4. Предъявление и приёмка

- [x] 4.1 Предъявить план пользователю, назвав решения, требующие подтверждения; проверка — получено явное решение «принят» или «не принят», молчание решением не считается
- [x] 4.2 При отказе: записать причину в журнал приёмки **до** внесения правок, поднять версию документа, доработать и предъявить снова; проверка — на каждую итерацию в журнале есть запись с причиной и ответной доработкой, номер версии документа увеличен
- [x] 4.3 При приёмке: записать решение «принят» в журнал приёмки с датой; проверка — запись присутствует, дальнейшие правки плана идут отдельными ревизиями

## 5. Завершение change

- [x] 5.1 Прогнать `openspec validate plan-extruder-development`; проверка — валидация проходит без ошибок
- [x] 5.2 После приёмки заархивировать change; проверка — change отсутствует среди активных в `openspec list`, а план остаётся доступным в `docs/project-plan.md`
- [x] 5.3 Создать первый change карты плана как отдельную работу; проверка — change создан командой `openspec new change`, его границы совпадают с этапом 0–1 карты
