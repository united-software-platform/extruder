## Context

Мотивация — [`proposal.md`](./proposal.md); требования — дельты
[`architectural-profile`](./specs/architectural-profile/spec.md)
и [`acceptance-run`](./specs/acceptance-run/spec.md).

Состояние на начало изменения задано `bootstrap-go-project`: `go.mod` с путём
`github.com/united-software-platform/extruder`, `cmd/extruder` печатает версию, модули
`internal/profile` и `internal/generation` существуют тремя слоями с одними `doc.go`, конфигурация
линтера — `.golangci.yml`, цели `go-build`, `go-test`, `go-lint`, `go-tools` в корневом `Makefile`
и их строки в белом списке `tools/host-runner/runner.py`.

Ограничения, формирующие подход:

- **Go в контейнере агента нет** ([DEC-040](../../../docs/extruder-design.md#устройство-extruder)):
  любая сборка, тест и линтер идут на хосте через раннер, целью `Makefile`.
- **Генератора ещё нет.** Накладок нет ни одной, поэтому прогон на этом изменении не может
  проверить ни один настоящий профиль — и всё же обязан быть работающим, а не декларативным.
- **Прогон первым зависит от двух предметов** — от профиля и от точки входа генератора, — которых
  в коде нет. Он и обязан их объявить
  ([DEC-042](../../../docs/extruder-design.md#проверки-и-поставка)).

## Goals / Non-Goals

**Goals:**

- Форма приёмочного прогона, не меняющаяся при добавлении накладок: прогон не знает ни языков,
  ни инструментов.
- Контракт точки входа генератора, скомпилированный вместе с вызывающей стороной, — чтобы три
  изменения Ядра заполняли готовую форму, а не договаривались о ней по ходу.
- Профиль и словарь значений как единый источник имён измерений для опроса, манифеста и накладок.
- Проверяемость самого каркаса при пустом фильтре.

**Non-Goals:**

- Устройство генератора: конвейер, модель проекта, рендер — `build-generation-pipeline`.
- Диагностика причины падения внутри сгенерированного проекта: прогон предъявляет вывод целей
  оснастки и не разбирает его.
- Производительность прогона: последовательность выбрана ради воспроизводимости, не ради скорости.

## Decisions

### Решение 1. Прогон — тест Go под тегом сборки

Каркас живёт в `test/acceptance/` с директивой `//go:build acceptance` и запускается целью
`go-acceptance`: `go test -tags acceptance ./test/acceptance` с явным `-timeout`. Тег выводит прогон
из `go test ./...`, то есть `go-test` остаётся быстрым.

Почему не иначе:

- **Отдельный бинарник `cmd/acceptance`** потребовал бы своего разбора аргументов, своего формата
  вывода и своей логики подсчёта, а главное — попал бы в поставку рядом с `extruder`.
- **Shell-скрипт** вывел бы фильтр и комбинаторику из-под тестов и линтера — ровно ту часть, где
  ошибка в отборе профилей тише всего.

Цена: тег сборки нужно не забыть передать линтеру — отсюда решение 10.

### Решение 2. Профиль — объект-значение с проверяющим конструктором

`internal/profile/domain`:

```go
type Language string      // go, python
type ProjectType string   // monolith, modular-monolith, service, distributed
type Architecture string   // clean-architecture, ports-adapters, layered
type Pattern string        // ddd, cqrs

type Profile struct { /* неэкспортируемые поля */ }

func NewProfile(lang Language, pt ProjectType, arch Architecture, patterns []Pattern) (Profile, error)
```

Конструктор отклоняет значение вне словаря, снимает повторы паттернов и приводит их порядок
к `ddd`, затем `cqrs` ([DEC-014](../../../docs/extruder-design.md#конвейер-генерации)). Поля
неэкспортируемые: профиль иммутабелен после создания
([DDD-013](../../../rules/ddd.md#value-object-ddd-012014)), а инварианты проверены один раз
при создании ([DDD-014](../../../rules/ddd.md#value-object-ddd-012014)).

Нормализация — не косметика: без неё `{cqrs, ddd}` и `{ddd, cqrs}` дают два разных профиля, число
96 перестаёт сходиться, а манифест становится недетерминированным.

Отвергнуто: структура из четырёх строк без проверок (недопустимое значение доживает до генерации)
и обобщённая `map[Dimension][]Value` (измерение становится строкой, которую никто не проверяет,
и [DEC-003](../../../docs/extruder-design.md#профиль) теряет смысл).

### Решение 3. Перечень всех 96 профилей — в домене

`profile.All() []Profile` плюс юнит-тест `len(All()) == 96`. «Допустимы все 96 сочетаний» —
это [DEC-001](../../../docs/extruder-design.md#профиль), правило предметной области, и в домене оно
проверяется тестом.

Отвергнуто: комбинаторика в пакете прогона. Там число 96 стало бы побочным результатом цикла:
пополнили словарь, не поправили прогон — и никто не заметил.

### Решение 4. Три свойства проверяются целями оснастки

Прогон вызывает `build`, `test`, `lint` в `Makefile` сгенерированного проекта — их наличие
гарантирует [DEC-017](../../../docs/extruder-design.md#состав-начальной-структуры). Прогон
не знает языка профиля и попутно проверяет саму оснастку, а не только код.

Отвергнуто: прогон знает язык и вызывает `go build`/`go test`/`golangci-lint` либо
`uv`/`pytest`/`ruff`. Это дублирует знание о языках и заставляет править прогон на каждом этапе
раскладок.

Цена: диагностика падения — вывод чужой цели; отсутствие цели отличается от её провала и даёт
отдельную причину вердикта.

### Решение 5. Контракт точки входа генератора

`internal/generation/application`:

```go
type GenerateStructureInput struct {
    Profile           profile.Profile
    ProjectIdentifier string
    TargetDir         string
}

type GenerateStructureUseCase interface {
    Execute(ctx context.Context, in GenerateStructureInput) error
}

var ErrNotImplemented = errors.New("...")

func NewGenerateStructure() GenerateStructureUseCase
```

Единственная публичная операция — [CLAR-008](../../../rules/clean-architecture.md#слой-приложения-clar-007013);
входной контракт неизменяем и логики не содержит — `CLAR-009`; прогон зависит от интерфейса,
а не от реализации — `CLAR-010`, и благодаря этому тест каркаса подставляет фейк (решение 9).

`TargetDir` во входном контракте: прогон пишет десятки разных каталогов, а фиксированная точка
монтирования ([DEC-009](../../../docs/extruder-design.md#целевой-каталог-и-запись)) — дело
`cmd/extruder`, которое подставляет её в тот же контракт.

Выходного контракта нет: прогон проверяет свойства через цели оснастки и выход не читает. Добавить
`Output` вправе та задача Ядра, которой он понадобится, — `DEC-042` это прямо разрешает.

Реализация на этом изменении одна — заглушка, возвращающая `ErrNotImplemented`. Прогон получает
генератор конструктором `NewGenerateStructure`, то есть контракт компилируется вместе
с вызывающей стороной: при интерфейсе без реализации прогон собирался бы против собственного фейка,
и первое изменение Ядра обнаружило бы, что настоящая сборка контракта никем не проверялась.
Возвращать из заглушки `nil` нельзя: тогда первый же реализованный профиль прошёл бы свойства
над пустым каталогом, если где-то ошибётся порядок проверок.

### Решение 6. Фильтр реализованных значений живёт в прогоне

Таблица реализованных значений — в пакете `test/acceptance`. Готовность накладки — свойство
реализации генератора, а не предметной области: домен, знающий, какие значения «уже сделаны»,
нарушает [CLAR-002](../../../rules/clean-architecture.md#слой-домена-clar-002004-clar-006)
и начинает расходиться со словарём.

Семантика — в дельте [`acceptance-run`](./specs/acceptance-run/spec.md): профиль берётся, если
реализованы его язык, тип проекта, архитектура и каждое значение набора паттернов; пустой набор
требований не предъявляет. Отсюда следствие, важное для этапов раскладок: профиль без паттернов
проверяем сразу, как готовы три обязательных измерения.

Отвергнуто: метод словаря в домене (см. выше) и файл данных YAML/JSON (добавляет разбор
и не проверяется линтером).

### Решение 7. Каталоги прогона и порядок

Сгенерированные проекты пишутся в `.gocache/acceptance/<профиль>` — `.gocache` уже игнорируется git
и уже служит каталогом кэшей целей Go. Каталог чистится в начале прогона, каталог прошедшего
профиля удаляется, каталог упавшего остаётся.

Отвергнуто: `t.TempDir()` — удаляет дерево упавшего профиля, то есть главную диагностику.

Прогон последовательный: цели оснастки дёргают общие кэши Go и сетевые установки Python,
параллельный прогон даст плавающие падения, которые дороже сэкономленных минут. Возврат
к параллельности — отдельное решение, когда время станет проблемой.

### Решение 8. Вывод прогона

Строка охвата «взято N профилей из 96», строка-вердикт на профиль, сводка «прошло/упало
из взятых». Каждый профиль — отдельный `t.Run`, прогон идёт до конца.

Fail-fast отвергнут: на этапах раскладок падают семейства профилей — «все `distributed`», «все
с `cqrs`», — и семейство видно только на полном прогоне; остановка на первом превращает разбор
в серию перезапусков по минутам каждый.

Число охвата — защита от риска «пустой фильтр читается как зелёная сборка», записанного
в [`project-plan.md`](../../../docs/project-plan.md#риски-и-ограничения). Падать при пустом фильтре
нельзя: на этом изменении он пуст штатно.

### Решение 9. Каркас проверяется фейковым генератором

Тест каркаса подставляет вместо заглушки фейк, который пишет минимальный проект — `Makefile`
с целями `build`, `test`, `lint`, — и каркас выполняет над ним все три свойства целиком: отбор,
генерацию, вызовы целей, вердикты, удаление каталога прошедшего профиля. Фейк живёт в пакете теста
и в бинарник не попадает.

Без этого при пустом фильтре настоящий генератор не вызывается ни разу, и весь код каркаса уходит
в Ядро непроверенным: первое падение будет непонятно чьим. Временный работающий генератор
в основном коде отвергнут — это мёртвый код в поставке.

### Решение 10. Линтер проходит и по тегированному коду

В цель `go-lint` добавляется `--build-tags acceptance`. Иначе в проекте появляется слепая зона
ровно там, где живёт комбинаторика отбора профилей.

### Решение 11. Каталог `test/` и действующие решения

`test/acceptance` — каталог приёмочного прогона, а не технический пакет модулей:
[DEC-039](../../../docs/extruder-design.md#устройство-extruder) дополняется оговоркой об этом.
Класть каркас внутрь `internal/generation/...` отвергнуто: тест-оснастка внутри доменного модуля
ломает границу модуля ([CLAR-022](../../../rules/clean-architecture.md#модульная-организация-clar-022023)).

Два новых решения вносятся в [`extruder-design.md`](../../../docs/extruder-design.md): `DEC-043` —
форма приёмочного прогона (тест под тегом сборки, три свойства через цели оснастки), `DEC-044` —
фильтр реализованных значений живёт в прогоне. На них будут ссылаться изменения Ядра, поэтому
им нужны номера в документе решений, а не только абзацы здесь
([TERM-001](../../../rules/terminology.md#единый-источник-определения)).

## Risks / Trade-offs

- **Правка `Makefile` и `tools/host-runner/runner.py`** → осознанное расхождение с поставкой kit'а
  по [DEC-033](../../../docs/extruder-design.md#проверки-и-поставка); состав расхождения назван
  в документе решений, при переустановке kit'а разрешается вручную.
- **Диагностика падения свойства — вывод чужой цели** → вердикт называет профиль, цель и каталог
  с сохранённым деревом; разбор идёт по дереву, а не по тексту.
- **Время прогона растёт произведением значений** → тег сборки держит прогон вне `go-test`;
  параллельность остаётся открытой возможностью с известной ценой (решение 7).
- **Инструменты обоих языков нужны на хосте** → до этапа «Раскладки Python» профили `python`
  в фильтр не входят; первый такой профиль упадёт в оснастке, и это ожидаемое, а не загадочное
  падение.
- **Пустой фильтр при зелёном прогоне** → строка охвата печатается всегда, и критерий готовности
  изменения требует увидеть в ней именно `0 из 96`.
- **Контракт зафиксирован до появления генератора** → правка контракта допустима, но только
  отдельной задачей в `tasks.md` того изменения, которому она понадобилась (`DEC-042`).
