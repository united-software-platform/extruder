# Проектные решения: план разработки Extruder

Решения, принятые для change `plan-extruder-development`: где живёт план, на какой технологии
реализуется Extruder, какой моделью решается задача профиля и как устроена приёмка плана.

## Context

Мотивация — в [`proposal.md`](./proposal.md), раздел `Why`.

Ограничения, формирующие подход:

- кода приложения в репозитории нет: архитектурные правила набора задают норму для создаваемого
  кода, а не описывают существующий;
- содержимое `openspec/changes/archive/` не читается никогда
  ([READ-004](../../../rules/reading-rules.md#запрет-каталогов-read-004)) — долгоживущие решения
  не могут храниться в артефактах change;
- инвентарь `openspec/specs/` пуст: поведение Extruder не описано ни одной спецификацией;
- Extruder обязан соответствовать тем же правилам, которые воплощает в генерируемых структурах —
  [Clean Architecture](../../../rules/clean-architecture.md), [DDD](../../../rules/ddd.md),
  [CQRS](../../../rules/cqrs.md).

## Goals / Non-Goals

**Goals:**

- зафиксировать носитель плана так, чтобы он оставался доступен агенту после архивации change;
- выбрать технологию реализации с обоснованием, пригодным для проверки решения позже;
- разложить задачу на последовательность change'ей обозримого размера;
- сделать приёмку плана явной процедурой с фиксацией причины отказа.

**Non-Goals:**

- проектирование внутреннего устройства Extruder до уровня компонентов и их контрактов — это
  предмет change'ей этапов 0–2;
- формат описания измерений (структура декларативных пакетов) — проектируется на этапе 4, когда
  появится хотя бы один живой случай;
- выбор конкретных библиотек CLI, TUI и шаблонизатора — решается в change этапа 1.

## Decisions

### Решение 1. Носитель плана — документ проекта, а не артефакт change

План разработки размещается в `docs/project-plan.md`.

| Вариант | Почему отклонён |
|---------|-----------------|
| `proposal.md` этого change | после архивации попадает под запрет чтения [READ-004](../../../rules/reading-rules.md#запрет-каталогов-read-004) — план перестанет быть доступен |
| `openspec/specs/<capability>/spec.md` | спецификация описывает поведение продукта, а не порядок работ; план требованием не является |
| `README.md` | адресован читателю извне, таблицу версий не ведёт ([DOC-022](../../../rules/documentation-rules.md#жизненный-цикл-документа)), а план — рабочий документ репозитория |
| незакреплённый change, который не архивируется | висящий change искажает картину активных работ и обходит процесс вместо следования ему |

`docs/project-plan.md` — файл самого проекта: `.sdd-kit-manifest.json` его не покрывает,
переустановка kit'а с ним не конфликтует.

### Решение 2. Технология реализации — Go

| Критерий | Go | Rust | Python | TypeScript/Node | PHP |
|----------|----|------|--------|-----------------|-----|
| Единый бинарник без рантайма у пользователя | да | да | нет | нет | нет |
| Шаблоны внутри артефакта поставки | `embed` (stdlib) | внешний крейт | `importlib.resources` | сборщик | phar |
| Абстракция файлового дерева в stdlib | `io/fs` | нет | нет | нет | нет |
| Виртуальная ФС для тестов в stdlib | `testing/fstest` | нет | нет | нет | нет |
| Шаблонизатор в stdlib | `text/template` | нет | нет | нет | нет |
| Скорость разработки | высокая | низкая | высокая | высокая | средняя |

Решающий довод — не популярность языка, а то, что стандартная библиотека Go содержит ровно те
три абстракции, из которых состоит Extruder: дерево файлов как интерфейс (`io/fs`), вшивание базы
знаний в бинарник (`embed`) и виртуальная ФС для тестов (`testing/fstest`). План структуры при
этом становится реализацией `fs.FS`, а не собственной моделью.

Второй довод — распространение: инструмент, создающий проекты на чужих языках, обязан
запускаться там, где нет ни Go, ни Python, ни Node. Единый статический бинарник это обеспечивает,
интерпретируемые кандидаты — нет.

Третий довод — самоприменимость: Go входит в перечень поддерживаемых языков, поэтому первый
бэкенд рендеринга пишется на том же языке, на котором написано ядро.

Rust даёт те же свойства распространения, но выигрыша не приносит при более высоком пороге и
меньшей скорости итераций. Python и TypeScript отклонены по требованию рантайма у пользователя,
PHP — по нему же и по отсутствию перечисленных абстракций.

### Решение 3. Двухфазная модель: язык подключается последним

```text
 +-----------+    +-------------------------+    +------------------+
 |  Профиль  |--->|   План структуры        |--->|  Дерево на диске |
 | яз/тип/   |    |   (модули, слои, роли)  |    |  (пути, файлы)   |
 | арх/пат   |    +-------------------------+    +------------------+
 +-----------+        ^        ^                        ^
                      |        |                        |
                 архитектура  паттерны                язык
                 тип проекта                    (бэкенд рендеринга)
```

Архитектура задаёт слои, паттерны — роли внутри слоёв, тип проекта — топологию модулей; все трое
работают в абстрактных понятиях. Язык переводит абстрактную роль в конкретный путь и содержимое
файла и влияет только на последний шаг.

Альтернатива — шаблон на каждую комбинацию профиля — отклонена: пять языков, четыре типа, четыре
архитектуры и подмножества из четырёх паттернов дают около 1280 шаблонов, причём каждый новый
язык умножает весь остальной объём. Двухфазная модель превращает произведение в сумму: новый язык
добавляется одним бэкендом и сразу работает со всеми архитектурами и паттернами.

Альтернатива без абстрактной фазы — оверлеи, напрямую накладывающие файлы друг на друга, —
отклонена: без промежуточного представления результат нельзя ни предъявить до записи, ни
проверить тестом без файловой системы.

### Решение 4. Определение готовности — собирающийся проект, а не дерево каталогов

Сгенерированная структура считается готовой, когда выполнены четыре условия:

```text
  тулчейн целевого языка собирает проект
  линтер целевого языка молчит
  тесты-заготовки проходят
  дерево совпадает с эталоном (golden)
```

Планка — «компилируется, линтер чист, тесты зелёные», но не «работает бизнес-логика»: заготовка
роли остаётся минимальной, однако обязана быть валидным кодом, а не пустым файлом.

Альтернатива — отдавать только дерево каталогов с пустыми заготовками — отклонена пользователем:
она вдвое дешевле, но результат непроверяем, и генератор пустых каталогов деградирует незаметно.

Следствия, влияющие на план:

- к дереву добавляется всё, без чего сборка невозможна: манифест модуля, точка входа, цель сборки,
  минимальный проходящий тест;
- появляется второй род тестов — приёмочные: генерация во временный каталог и запуск тулчейна
  целевого языка. Golden-тесты остаются быстрой проверкой в памяти;
- каждый поддержанный язык требует своего тулчейна в окружении проверки, что ставит естественный
  предел темпу добавления языков;
- шаблоны ролей содержательны с самого начала, поэтому формат декларативных пакетов проектируется
  под шаблоны с телом и подстановками, а не под перечень путей.

### Решение 5. Знание об измерениях выносится в декларативные пакеты, но не с первого дня

Этапы 1–3 держат знание об измерениях в коде Go. Этап 4 выносит его в декларативные пакеты
(описание измерения плюс шаблоны ролей), вшиваемые через `embed`, с возможностью подключить
внешний каталог.

Критерий приёмки этапа 4 — поведение этапа 3 не изменилось: вынос не должен ничего сломать.

Альтернатива «сразу пакеты» отклонена: формат описания измерений проектировался бы вслепую, до
появления хотя бы одного работающего случая. Альтернатива «навсегда в коде» отклонена: добавление
языка стало бы правкой ядра, а не добавлением контента.

### Решение 6. Несочетаемые комбинации генерируются с предупреждением

README объявляет измерения независимыми: значение одного не ограничивает выбор в остальных.
Практические несочетаемости (например, тяжёлый DDD-оверлей поверх идиоматичного Go) не
запрещаются, а сопровождаются предупреждением.

Альтернатива «запрещать» противоречит объявленной независимости измерений и требует ведения
матрицы запретов. Альтернатива «молчать» лишает пользователя сигнала о заведомо спорном
сочетании.

### Решение 7. Один change на этап; план — карта change'ей

План перечисляет последующие change'и по имени, с границами и критерием готовности каждого.
Change'и создаются по одному, после приёмки плана, а не пакетом.

```text
  этап 0-1  ->  bootstrap-extruder-cli          модель профиля и CLI; на диск не пишет
  этап 2    ->  add-structure-plan               абстрактный план, golden-тесты
  этап 3    ->  render-plan-to-filesystem        собирается: сборка, линтер, тесты зелёные
  этап 4    ->  extract-dimension-packs          знание -> декларативные пакеты
  этап 5-7  ->  по одному change на измерение    архитектуры, паттерны, типы проекта
  этап 8    ->  add-second-language-backend      экзамен архитектуры: ядро не правится
```

Этап 8 стоит до расширения контента намеренно: это проверка правильности разделения на этапе 2, а
не функциональность. Узнать о неверном разделении нужно до того, как накоплены четыре архитектуры
и три паттерна.

Альтернатива — один change на весь фундамент — отклонена пользователем: такой change нельзя ни
принять, ни отклонить целиком, а его объём не поддаётся оценке.

### Решение 8. Журнал приёмки — отдельный раздел документа плана

Документ плана содержит два разных журнала:

| Раздел | Отвечает на вопрос |
|--------|--------------------|
| «Журнал приёмки» | какое решение принял пользователь, по какой причине отклонил, что изменено в ответ |
| «Версионирование» ([DOC-022](../../../rules/documentation-rules.md#жизненный-цикл-документа)) | что изменилось в документе от версии к версии |

Причина отказа фиксируется до начала доработки: запись причины после правки превращает журнал в
пересказ уже сделанного.

Альтернатива — вести только таблицу версий — отклонена: она фиксирует содержание правки, но не
решение пользователя и не причину, по которой правка потребовалась.

### Решение 9. Первый вертикальный срез — Go, сервис, Layered, без паттернов

Самая простая комбинация: один модуль, набор слоёв без оверлеев. Она проходит через все фазы
модели и потому проверяет ядро, не создавая объёма контента.

## Risks / Trade-offs

- **Карта change'ей окажется неверной после этапа 2** (реальное устройство плана структуры
  разойдётся с ожиданием) → план версионируется как обычный документ; расхождение фиксируется
  ревизией плана, а не молчаливым отклонением от него.
- **Приёмочные тесты требуют тулчейна целевого языка, которого нет в контейнере агента** →
  golden-тесты остаются полной проверкой логики и выполняются везде; приёмочные выполняются там,
  где тулчейн доступен. Отсутствие тулчейна не должно превращаться в отказ от варианта Б.
- **Язык может протечь в абстрактную фазу** незаметно, и обнаружится это только на втором языке →
  ранний экзамен на этапе 8 до накопления контента; критерий — ядро не правится ни строкой.
- **Цикл приёмки может зациклиться** при неограниченном числе итераций → каждая итерация
  адресует конкретную зафиксированную причину отказа; причина без записи в журнал доработку не
  запускает.
- **Поведение Extruder не описано спецификациями** из-за `skip_specs` этого change → первые
  дельта-спеки создаются в change этапов 0–1, где появляется первое наблюдаемое поведение.
- **Планка «собирается» замедляет добавление языков** → это осознанная цена варианта Б: она же
  не даёт накопить непроверенные бэкенды.

## Migration Plan

Развёртывания и обратной совместимости change не затрагивает: он добавляет один документ.

```text
  1. создать docs/project-plan.md по решениям этого документа
  2. предъявить план пользователю
  3. отказ  -> причина в «Журнал приёмки» -> доработка -> шаг 2
     приёмка -> архивация change
  4. создать первый change карты (bootstrap-extruder-cli)
```

Откат — удаление `docs/project-plan.md`; последствий для кода и окружения нет, поскольку ни того,
ни другого change не касается.

## Open Questions

- Какой язык станет вторым бэкендом — PHP или Python. Решается к этапу 8; на устройство ядра и
  разбиение работ не влияет.
- Какой архитектурный линтер закрепить для Go-бэкенда, чтобы проверять направление зависимостей
  [CLAR-001](../../../rules/clean-architecture.md#слои-и-направление-зависимостей-clar-001) в
  сгенерированном проекте. Кандидат рассматривается после этапа 8.
- Имя и формат файла профиля внутри сгенерированного проекта. Нужен начиная с этапа 9;
  на этапы 1–8 не влияет.
